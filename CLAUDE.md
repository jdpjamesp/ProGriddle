# ProGriddle conventions

ProGriddle: allowing you to cook up new grid based games easily. An OpenEdge ABL OO framework for grid based games. Target: OpenEdge 12.8, Windows, prowin GUI via WinForms and the ABL .NET bridge. Namespace and source root: `ProGriddle` (`src/ProGriddle/...`). The build brief is `PROGRIDDLE_PLAN.md` (local only, not in git).

## Rules
- OpenEdge ABL OO only. One class per file. Namespace matches folder path.
- Always use `USING` statements, never fully qualified names inline. ALWAYS use the wildcard form, one line per namespace, for example `USING ProGriddle.Games.Life.*.`, `USING ProGriddle.Core.*.`, `USING OpenEdge.Core.*.`, `USING Progress.Lang.*.`. Never write one `USING` per class. This also covers the class's own namespace. Only .NET types stay specific where a wildcard would clash, for example `USING System.Windows.Forms.Timer FROM ASSEMBLY.` (the layering check reads both forms).
- Program against interfaces. Concrete classes are created only in composition roots (the `run-*.p` files and tests).
- Prefer `FINAL` on classes not designed for inheritance. Mark abstract methods explicitly.
- No object allocation inside per cell loops.
- Every class file has `BLOCK-LEVEL ON ERROR UNDO, THROW.` between the USING statements and the CLASS statement. Without it, `UNDO, THROW` prints the message and execution carries on instead of unwinding. A class also needs a `USING` for its own name before it can use its own type.
- Every MEMPTR must be reset to size 0 (`SET-SIZE(m) = 0`) as soon as it is finished with, so memory never leaks. A MEMPTR allocated inside a method is freed in that method's `FINALLY` block. A MEMPTR owned by an object is freed in a `Dispose` method, with a destructor as a safety net, and the object's owner calls `Dispose`.
- Named values are `ENUM`s, never include files full of `&GLOBAL-DEFINE` or `&SCOPED-DEFINE` lists. Phases, modes, kinds, view codes, palette and picture names, anything that is a set of names for the cases of one idea, is an enum in its own file (one enum per file, see `GameCommand`, `GamePhase`, `Palette`), so it is typed, namespaced and cannot clash with another game's names. Use `INTEGER(Enum:Member)` where a value has to go into a cell store, and `Enum:GetEnum(n)` to go back. Use "unknown" (`?`) for "none", not a 0. Preprocessor constants are still fine for plain quantities (a board size, a frame count, a speed) and for a macro, and an include is still right for shared code such as a temp-table definition (`SparseCells.i`).
- Never name a method `Clone`, `Equals` (unless overriding), `ToString` (unless overriding) or any other inherited `Progress.Lang.Object` member by accident. The cell store copy method is `Duplicate`.
- ABLUnit fixture annotations are the reverse of JUnit: `@Setup` and `@TearDown` run around every test, while `@Before` and `@After` run once per class. ABLUnit also does not run `@Test` methods inherited from a base class.
- Choose between several values of one thing (an enum, a name, a cue number) with `CASE ... WHEN ... OTHERWISE ... END CASE`, never a chain of `IF ... THEN RETURN`: `CASE poCue: WHEN AsteroidsCue:Fire THEN ...` works on an enum, `WHEN A OR WHEN B` joins values, and `OTHERWISE` is where an unknown value is thrown or defaulted.
- Throw `ProGriddle.Core.GridException` (or a subclass) for contract violations, never return magic values silently.
- All randomness goes through an injectable seeded random source so tests are deterministic.
- Every public method has a test. Write the test first where practical.
- No em dashes anywhere in code comments, docs, commit messages or console output. Use commas, colons or hyphens instead.
- Keep commits small, one per sub step, with a clear message.
- Documentation layout: `README.md` documents the framework and how to create a new game with it. Every implemented game has its own page, `docs/games/<game>.md`, written as part of that game's work. A game phase is not done until its page exists and the README links to it. Game specific material (controls, settings, timings, design notes) belongs on the game page, not in the README.
- .NET types (`System.Windows.Forms`, `System.Drawing`) are referenced only inside `ProGriddle.UI.WinForms`. Core, Engine and Games must compile and test without a GUI.
- Dispose .NET objects (brushes, pens, bitmaps, timers) deterministically. Unsubscribe from .NET events when the form closes.
- Never run long computation on the UI thread without yielding. Large Life boards must stay responsive.
- If the framework needs changing to support a game, change the framework and update its tests. Do not special case a game inside Core.
- Use the progress-abl skill when writing or reviewing ABL.

## Layering (checked by tools/check-layering.ps1)
Core depends on nothing. Engine depends on Core. UI.Text depends on Core and Engine. UI.Audio (the Windows sound player, with its one procedure file WinMm.p for the winmm calls that a class cannot declare) depends on Core and Engine only, and no game may use it. UI.WinForms depends on Core, Engine and UI.Text and is the only layer that may use .NET. Games depend on Core and Engine only and never on another game or on UI.WinForms.

## Commands
- Tests: `powershell -NoProfile -ExecutionPolicy Bypass -File tools/run-tests.ps1 [-Filter "Grid*"] [-Gui] [-All]`. The default runs everything except `tests/**/UI/WinForms`, under `_progres -b`. `-Gui` runs only the WinForms tests, under `prowin -b` (results in `build/test-results/gui/results.xml`). `-All` runs both.
- Layering: `powershell -NoProfile -ExecutionPolicy Bypass -File tools/check-layering.ps1`
- Conventions audit (header comments, BLOCK-LEVEL, wildcard USING, no dashes, MEMPTR freed, public members tested, no include files that hold lists of constants; needs no OpenEdge): `powershell -NoProfile -ExecutionPolicy Bypass -File tools/audit-conventions.ps1`
- New game from the template: `powershell -NoProfile -ExecutionPolicy Bypass -File tools/new-game.ps1 -Name Snake -Title "Snake" -Blurb "..."`. After changing `templates/game` or the interfaces a game implements, run `tools/check-template.ps1` (it makes a game, tests it and deletes it)
- Compile everything and list every error at once: `powershell -NoProfile -ExecutionPolicy Bypass -File tools/compile.ps1 [-SourceOnly]`
- Run the real window and check it: `powershell -NoProfile -ExecutionPolicy Bypass -File tools/gui-smoke-life.ps1` (it takes over the keyboard and mouse for about 40 seconds, so warn the user first)
- Play any game from one window, the arcade (the ProGriddle Cookoff), by double clicking `cookoff.bat` in the repository root or with this: `prowin.exe -T "%TEMP%\ProGriddle" -l 1024 -p tools/launch.p -param "run/run-arcade.p"`. It lists every `run/run-*.p` by itself (a new game needs only its run file, ideally with an `Arcade: Title | blurb` line in its header comment, and `Arcade: hidden` for a run file that is not a game). Its window check is `tools/gui-smoke-arcade.ps1` (takes over the keyboard and mouse for under a minute, so warn the user first)
- Play Life: `prowin.exe -T "%TEMP%\ProGriddle" -l 1024 -p tools/launch.p -param "run/run-life.p"` from the repository root
- Play Battleships: `prowin.exe -T "%TEMP%\ProGriddle" -l 1024 -p tools/launch.p -param "run/run-battleships.p"`. Its window check is `tools/gui-smoke-battleships.ps1` (takes over the keyboard and mouse for a couple of minutes, so warn the user first). The two smoke tests share `tools/gui-smoke-common.ps1`
- Play Minesweeper: `prowin.exe -T "%TEMP%\ProGriddle" -l 1024 -p tools/launch.p -param "run/run-minesweeper.p"`. Its window check is `tools/gui-smoke-minesweeper.ps1` (also takes over the keyboard and mouse, for a couple of minutes, so warn the user first)
- Play Tetris: `prowin.exe -T "%TEMP%\ProGriddle" -l 1024 -p tools/launch.p -param "run/run-tetris.p"`. Its window check is `tools/gui-smoke-tetris.ps1` (also takes over the keyboard and mouse, for a couple of minutes, so warn the user first). The picture is drawn by `TetrisPainter` on a pixel canvas (the "Lantern Glass" look of `docs/design/tetris-art.md`: blocks in `TetrisArt`, colours in `TetrisLook` and the `Tint` enum), the effects are functions of the game's own clock (`Animated`, `ClearDelayMs`, `ElapsedMs` and the `Last...Ms` readers), and `TetrisInput:BannerText` is always empty because the painter draws PAUSED and GAME OVER
- Play 2048: `prowin.exe -T "%TEMP%\ProGriddle" -l 1024 -p tools/launch.p -param "run/run-2048.p"`. Its window check is `tools/gui-smoke-2048.ps1` (also takes over the keyboard and mouse, for a minute or two, so warn the user first). Its namespace is `ProGriddle.Games.2048` because a namespace may start with a digit but a class name may not, so its classes are `Tiles...`
- Play Snake: `prowin.exe -T "%TEMP%\ProGriddle" -l 1024 -p tools/launch.p -param "run/run-snake.p"`. Its window check is `tools/gui-smoke-snake.ps1` (also takes over the keyboard, for a minute or two, so warn the user first). The picture is drawn by `SnakePainter` on a pixel canvas (the "Lantern Glass" look of `docs/design/snake-art.md`: tiles in `SnakeArt`, colours in `SnakeLook` and the `SnakeTint` enum), the effects are functions of the game's own clock (`Animated`, `ElapsedMs` and the `...Ms` readers), `SnakeInput:BannerText` is always empty because the painter draws the words, and `GridView:FitToWindow` scales the canvas to fill the window (Tetris and Snake use it)
- Sound (Tetris, Snake, Space Invaders and Asteroids, on by default; the other games stay silent on purpose): see `docs/framework/sound.md`. A recipe such as `t523:60:30,t659:110:70` becomes 8 bit sound with `ToneSynth` (Engine, integer maths), a `SoundBank` holds the sounds by cue number (`INTEGER(TetrisCue:Lock)`), a per game `ICueSource` (`TetrisCues`, `SnakeCues`, `InvadersCues`, `AsteroidsCues`) says what is new by comparing the game's counters (an `ILoopSource` says which looping sounds, recipes starting with `@`, should be sounding now), `SoundRenderer` wraps the painter and plays it, and `WaveOutPlayer` (UI.Audio, with the one procedure file `WinMm.p`) plays it through winmm. Settings `sound.on` and `sound.volume`, the M key. Dispose the player before the bank. The window smoke tests cannot hear
- Play Asteroids: `prowin.exe -T "%TEMP%\ProGriddle" -l 1024 -p tools/launch.p -param "run/run-asteroids.p"`. The shapes are in `AsteroidsArt.cls` and the colours in `AsteroidsLook.cls` (one place each, from `docs/design/asteroids-art.md`), and the speed is a percentage of the real 60 frames a second (`asteroids.speed`, + and - keys, starts at 80). Its window check is `tools/gui-smoke-asteroids.ps1` (also takes over the keyboard, for about a minute, so warn the user first); `tools/look-asteroids.ps1` saves a title screen screenshot without keys. Tests drive it frame by frame with `Advance`, and `Drawing` can be switched off so a test that only cares about the rules does not draw every frame
- Play Space Invaders: `prowin.exe -T "%TEMP%\ProGriddle" -l 1024 -p tools/launch.p -param "run/run-spaceinvaders.p"`. Its window check is `tools/gui-smoke-spaceinvaders.ps1` (also takes over the keyboard, for about a minute, so warn the user first); `tools/look-spaceinvaders.ps1` saves a title screen screenshot without keys. The art is in `InvadersArt.cls` and the colours in `InvadersLook.cls` (one place each, sizes must stay), and the speed is a percentage of the arcade's 60 frames a second (`spaceinvaders.speed`, + and - keys)

## Environment notes (found in Phase 0 and 3)
- Under `prowin -b` WinForms objects can be built and drawn (`DrawToBitmap`) but there is no .NET message loop, so timers never tick and `Application:Run` fails. `Application:DoEvents` is forbidden in ABL anyway. Anything that needs real ticks or real input is checked in a windowed run.
- ABL cannot override the .NET `Dispose`, so a control that owns memory exposes `ReleaseResources` and its owner calls it.
- Names that look harmless but are ABL keywords and cannot be variable or statement-style method names: `text`, `entry`, `by`, `old`, `line`, `clear` (call it `ClearBoard`), `pause`, `undo`, `run`.
- An ABL `CHARACTER` under `prowin` is ISO 8859-1, so a flag or a bomb becomes `?`. Pass such text to .NET as a UTF-8 `LONGCHAR` (see `GridView:SetGlyphs`). Never write `*/` inside a comment, even in an example string. In a string literal `~` is the escape character (`"~o"` is just `"o"`), and string comparison ignores case, so `"X"` equals `"x"`: do not use letters that differ only by case as distinct symbols.
- The PROPATH environment variable is ignored by `_progres`. `tools/run-tests.p` sets PROPATH in code.
- ABLUnit exits 0 even when tests fail. `tools/run-tests.ps1` reads `build/test-results/results.xml` and sets the exit code itself.
- The ABLUnit output folder must exist before the run (the script creates it).
